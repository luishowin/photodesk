PhotoDesk

A display-referred photo editor for Fedora / GNOME.

Its native subject is a finished image — an iPhone HEIF, a JPEG, a screenshot — that already has a rendering intent baked in by the device that made it.

It is not a RAW laboratory. It doesn't reconstruct scene radiance, doesn't ask you to pick a demosaic algorithm or a view transform. RAW is an input, not a worldview.

The test for any feature: does it shorten the path between opening a photo and being happy with it?

Status — v0.0 · pre-code · spec v0.4

There is no application yet, and that is on purpose. Three spikes come before any product code, on the argument that discovering their answers in month four is far more expensive than spending three weeks on them now.

The governing principle

Freeze interfaces and invariants early. Freeze implementation choices only after a spike proves them.

Two rules follow, and the project is held to both. Every frozen item carries a written reason — if it can't be justified in a sentence, it isn't frozen, it's a habit. Every provisional item names the spike that resolves it — "provisional" without an exit condition is just indecision with better PR.

Phase 0 — before any product code

Spike A — fork audit

Classify every RapidRAW subsystem as KEEP, ADAPT, REPLACE or AVOID. Four gate criteria, all of which must hold — otherwise the fork doesn't happen and RapidRAW becomes an architectural reference instead. A fork you have to rewrite is slower than building from scratch, and you'd discover it in month four.

Spike B — colour validation harness

Prove linear Display P3 f16 rather than assuming it, against a corpus with known values and ΔE2000 thresholds. The test that matters most is a deep-shadow ramp: half float has ~11 bits of significand, and linear encoding spends most of them on highlights where the eye cares least. Built standalone so it survives either fork outcome, and kept afterwards as a permanent suite.

Spike C — preview renderer

Establish whether one shader source can drive both preview and export on this platform. Scouting has already found that RapidRAW's chain is compute end to end, and WebGL2 has no compute shaders, no storage textures and no storage buffers — so hand-writing the preview chain is the expected outcome rather than a contingency.
